Money moves when the proof does.

The buyer describes a deal in one sentence. Claude turns it into checkable conditions, both sides sign the contract with keys kept on their own devices, and PayPal authorizes the buyer's payment without capturing it. The seller uploads proof, Claude judges each condition, and fixed code decides whether to capture (release the money), ask for a fix, send it to the buyer, or void the hold. The model never moves money. A pure function does.

The idea in six steps

What makes it trustworthy

The model never touches money

Claude only returns pass, fail or unclear with a confidence for each condition. decide() is a pure function with fixed thresholds that both parties signed. It is the only path to capture or void, and a test pins that.

A signed contract gates every payment step

Each side signs a canonical JSON contract with ECDSA P-256 using a key that never leaves the browser. Before an order, an authorization, a capture or a payout, the server rebuilds the contract from the database and checks both signatures.

An audit trail that cannot be rewritten

Every change writes a deal_events row, and a Postgres trigger blocks UPDATE and DELETE on that table. Every PayPal call carries a fixed idempotency key, and every PayPal fact is applied at most once.

Use cases

Any deal between two people who don't trust each other yet, where the proof can be photographed or tracked. Pick a scenario to see how Handshake runs it. The first three are the shipped demo presets; the rest show where the same engine fits.

Who it is for

  • Marketplace buyers paying strangers on Facebook Marketplace, Craigslist, Discord or Reddit, where "Goods & Services" protection is weak or missing.
  • Sellers who want proof that the buyer has funds before they ship. The hold is real money on the buyer's card.
  • Freelancers and makers doing commissions: custom furniture, art, repairs.
  • Platforms that want escrow-like assurance without becoming a licensed escrow service. The hold stays with PayPal.

Why not plain escrow?

Escrow needs a human agent and days of review. Handshake settles a clear case in under 15 seconds. Only the unclear ones go to the buyer, and the 21-day cap means a hold never outlives PayPal's 29-day authorization window.

Architecture

It is one Next.js 16 app (App Router, Node runtime), one Postgres 18 database and one cron job, all on Render. Everything about deals goes through one deep module, lib/deal, which talks to the outside through four ports (db, paypal, ai, email) plus a clock. Tests swap the ports for fakes. Click any box.

Decision engine simulator

This is a live copy of decide() from lib/deal/decide.ts. Set each condition's verdict and confidence, the amount and the attempt number, and watch the decision change. Both thresholds are snapshotted into the signed contract when the deal is created.

The rules, in order
  1. No conditions → buyer review (unclear)
  2. Any fail: on the first submission → request a fix. On the second → void if any fail has confidence ≥ threshold, otherwise buyer review.
  3. Any unclear → buyer review
  4. Any confidence < threshold → buyer review (low confidence). Exactly 0.85 passes.
  5. Amount > auto-capture max → buyer review. Exactly $200 captures.
  6. Otherwise → capture

Before Claude is called, hashCheck() compares the evidence photos with the listing photos by SHA-256. A reused photo fails every photo condition at confidence 1 without a model call (guardrail-v1).

Security model

Defense in depth around one rule: money moves only when the code decides, and only within the signed contract. Every row below names the code that enforces it and the test that proves it (06 "Security checks", all ticked).

Encryption at rest

AES-256-GCM through lib/crypto/seal.ts, with a keyring in DATA_KEYS. The first key encrypts and any listed key decrypts. The AAD binds each value to table.column:deal id, so a ciphertext copied to another row fails to decrypt. Sealed fields: the deal's sentence and title, condition text, evidence values, verdict reasons and raw model output, photo bytes, sensitive event payload keys, and TOTP secrets. True zero-knowledge end-to-end encryption is not possible here, because Claude must read the terms. This is the honest alternative: TLS in transit, sealed at rest, and signatures for integrity.
